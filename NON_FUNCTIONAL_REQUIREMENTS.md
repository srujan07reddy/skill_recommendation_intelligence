# NON-FUNCTIONAL REQUIREMENTS## Student Skill Intelligence Platform (SSIP)**Document:** NON_FUNCTIONAL_REQUIREMENTS.md  **Version:** 1.0  **Status:** Initial Development Specification  **Architecture:** Stateless, Session-Based Web Application---# 1. Introduction## 1.1 PurposeThis document defines the non-functional requirements of the Student Skill Intelligence Platform (SSIP).It establishes the expected quality attributes, performance standards, security requirements, operational constraints and reliability expectations of the application.These requirements shall guide system architecture, implementation, testing, deployment and future optimization.## 1.2 ScopeThe non-functional requirements apply to:- Frontend application.- Backend application.- Authentication and authorization.- Temporary session management.- File ingestion and processing.- Skill intelligence engine.- Recommendation engine.- Dashboard and visualization.- Export generation.- Production deployment infrastructure.---# 2. Performance Requirements## NFR-PER-001: Application Response Time**Priority:** Must HaveThe application shall provide responsive interactions under normal operating conditions.Target response times:| Operation | Target ||---|---:|| Initial page rendering | Within 3 seconds || Dashboard navigation | Within 2 seconds || Standard API requests | Within 2 seconds || Filter application | Within 2 seconds || Session status retrieval | Within 1 second || Authentication response | Within 2 seconds |These targets exclude unusually large file processing and external network delays.## NFR-PER-002: Dataset ProcessingThe system shall process uploaded datasets efficiently.Initial performance targets:- 1,000 student records: within 5 seconds.- 5,000 student records: within 15 seconds.- 10,000 student records: within 30 seconds.These are initial engineering targets to be validated through benchmarking on the selected hosting configuration.## NFR-PER-003: Memory ManagementThe backend shall manage temporary memory consumption efficiently.Requirements:- Avoid unnecessary dataset duplication.- Release references to processed datasets when sessions expire.- Avoid loading multiple large datasets simultaneously without resource checks.- Monitor memory consumption during file processing.- Prevent one analysis session from exhausting resources needed by other sessions.## NFR-PER-004: Concurrent ProcessingThe application should support multiple users accessing the platform simultaneously.Initial target:- 50 concurrent authenticated users.- 10 simultaneous student assessment or analysis sessions.The system shall enforce resource limits to prevent excessive concurrent processing.## NFR-PER-005: Dashboard PerformanceAnalytical dashboards shall render efficiently.Large tables should support pagination, filtering and controlled data loading rather than rendering every record simultaneously.Charts shall use precomputed analytical summaries where possible.---# 3. Scalability Requirements## NFR-SCL-001: User ScalabilityThe architecture shall support an increasing number of students, faculty members, HODs and Deans without requiring a fundamental redesign.## NFR-SCL-002: Department ScalabilityThe application shall support multiple academic departments and their associated skill assessment sessions.## NFR-SCL-003: Dataset ScalabilityThe ingestion pipeline shall support increasing dataset sizes through configurable upload and processing limits.## NFR-SCL-004: Processing ScalabilityThe application shall allow independent scaling of frontend delivery and backend processing resources.## NFR-SCL-005: Modular ExpansionNew analytical modules, skill categories and recommendation rules shall be introduced without requiring substantial changes to unrelated application modules.---# 4. Security Requirements## NFR-SEC-001: Secure Communication**Priority:** CriticalAll production application communication shall use HTTPS.Sensitive information must not be transmitted through unencrypted connections.## NFR-SEC-002: Authentication SecurityThe application shall use secure authentication mechanisms.Requirements:- Secure credential handling.- Protected authentication tokens or cookies.- Session expiration.- Secure logout.- Protection against common authentication attacks.Where possible, university authentication services should be reused.## NFR-SEC-003: AuthorizationThe backend shall enforce role-based access control.Users must not be able to access information outside their assigned permissions by manipulating frontend requests or API parameters.## NFR-SEC-004: Session IsolationTemporary analysis sessions must remain logically isolated.A user must not be able to retrieve another user's session data without explicit authorization.## NFR-SEC-005: File Upload SecurityThe application shall protect against malicious or malformed uploaded files.Controls shall include:- File size restrictions.- Extension validation.- File content inspection.- Safe parsing.- Protection against malicious spreadsheet content.- Rejection of unsupported formats.Uploaded spreadsheet formulas and macros must never be executed by the application.## NFR-SEC-006: Input ValidationAll user inputs shall be validated on the backend.The application shall protect against common web application vulnerabilities, including:- Cross-Site Scripting (XSS).- SQL Injection where database-backed components exist.- Cross-Site Request Forgery (CSRF), where applicable.- Broken Access Control.- Insecure Direct Object Reference.- Injection attacks.- Malicious file uploads.## NFR-SEC-007: Secure Export GenerationExport files containing identifiable student information shall only be generated for authorized users.Download endpoints shall verify the user's access permissions and the associated analysis session.## NFR-SEC-008: Security LoggingSecurity events shall be logged without unnecessarily retaining student assessment contents or sensitive personal information.## NFR-SEC-009: Dependency SecurityThird-party dependencies shall be reviewed and updated to address known vulnerabilities.---# 5. Privacy and Data Protection Requirements## NFR-PRV-001: No Permanent Student-Skill Database**Priority:** CriticalThe application shall not maintain a permanent database of student skill assessment records.Student skill information shall be processed through temporary session-based mechanisms.## NFR-PRV-002: Data MinimizationThe application shall collect only information required for skill analysis and institutional decision-making.Unnecessary personal information shall not be requested.## NFR-PRV-003: Temporary Data RetentionStudent assessment records shall remain available only during the configured temporary session lifecycle.## NFR-PRV-004: Automatic Data CleanupExpired sessions shall trigger cleanup of:- Student assessment records.- Uploaded source files.- Normalized datasets.- Temporary analytical results.- Generated server-side export files.## NFR-PRV-005: Restricted LoggingRaw student datasets, credentials and sensitive identifiers shall not be written into application logs.## NFR-PRV-006: Export PrivacyReports-only exports shall use aggregated information and avoid exposing identifiable student records by default.Complete analysis packages shall require appropriate authorization.## NFR-PRV-007: Browser Data ProtectionSensitive assessment information shall not be unnecessarily retained in browser storage, caches or client-side persistent state.## NFR-PRV-008: Data Deletion VerificationThe application shall provide a mechanism to verify that expired sessions and their associated temporary files have been removed.The cleanup mechanism shall account for application memory, temporary file directories and any configured ephemeral storage.---# 6. Reliability and Availability Requirements## NFR-REL-001: Application Availability**Priority:** HighThe production application should target 99.5% monthly availability, excluding scheduled maintenance and external infrastructure failures.## NFR-REL-002: Graceful FailureThe application shall handle unexpected processing errors without exposing internal implementation details.Users shall receive understandable error messages.## NFR-REL-003: Server Restart BehaviourBecause the architecture uses temporary in-memory sessions, the system shall not guarantee recovery of active analysis data after an unexpected backend restart.The application must detect unavailable sessions and communicate the situation to affected users.## NFR-REL-004: Resource IsolationResource-intensive analysis sessions shall not unnecessarily interfere with unrelated application operations.## NFR-REL-005: Export ReliabilityThe application shall validate generated exports before making them available for download.Incomplete or corrupted exports shall not be presented as successful downloads.## NFR-REL-006: Cleanup ReliabilityTemporary data cleanup shall operate independently of normal user navigation.Session expiration must not depend solely on users closing their browser windows.---# 7. Usability Requirements## NFR-USA-001: User InterfaceThe application shall provide a clear, consistent and accessible interface for all authorized user roles.## NFR-USA-002: Responsive DesignThe application shall support:- Desktop computers.- Laptops.- Tablets.- Mobile browsers.The primary analytical dashboard shall be optimized for desktop usage.## NFR-USA-003: NavigationUsers shall be able to navigate between authorized modules without unnecessary complexity.## NFR-USA-004: Data VisualizationCharts and tables shall clearly communicate departmental skill distributions, proficiency patterns and competency deficiencies.## NFR-USA-005: Error CommunicationValidation failures and processing errors shall be communicated using understandable messages.## NFR-USA-006: Assessment ExperienceStudent assessment forms shall be easy to understand and complete.Form validation shall identify missing or incorrect information before submission.## NFR-USA-007: AccessibilityThe application should follow WCAG 2.1 AA accessibility principles where applicable.---# 8. Maintainability Requirements## NFR-MNT-001: Modular ArchitectureThe application shall follow a modular monolithic architecture.Frontend presentation, API handling, data processing, session management, analysis and export generation shall remain logically separated.## NFR-MNT-002: Code QualityThe codebase shall follow consistent naming conventions, formatting standards and documented development practices.## NFR-MNT-003: Configuration ManagementEnvironment-specific settings shall be maintained through configuration files and environment variables.Sensitive credentials must not be committed to source control.## NFR-MNT-004: DocumentationEach major module shall maintain relevant technical documentation.## NFR-MNT-005: TestabilityBusiness logic shall be designed to support independent unit and integration testing.## NFR-MNT-006: Change ManagementChanges to recommendation rules, proficiency criteria and data structures shall be version-controlled and documented.---# 9. Compatibility Requirements## NFR-COMP-001: Browser CompatibilityThe application shall support current stable versions of:- Google Chrome.- Microsoft Edge.- Mozilla Firefox.- Safari.## NFR-COMP-002: File CompatibilityThe ingestion system shall support valid Excel XLSX and CSV datasets.## NFR-COMP-003: Export CompatibilityGenerated reports shall be compatible with commonly used spreadsheet and PDF applications.## NFR-COMP-004: API CompatibilityFrontend and backend communication shall use documented REST API contracts with consistent request and response structures.---# 10. Deployment and Infrastructure Requirements## NFR-DEP-001: Live WebsiteThe application shall be accessible through a registered production domain using HTTPS.## NFR-DEP-002: Frontend HostingThe React frontend shall support deployment through Vercel.## NFR-DEP-003: Backend HostingThe FastAPI backend shall operate on the selected BigRock VPS using a supported Linux environment.## NFR-DEP-004: ContainerizationThe application should use Docker and Docker Compose for consistent local development and production deployment.## NFR-DEP-005: Reverse ProxyNginx shall manage HTTPS termination and routing between frontend and backend services where applicable.## NFR-DEP-006: Environment SeparationDevelopment, testing and production environments shall use separate configurations.## NFR-DEP-007: Resource MonitoringThe production environment shall monitor:- CPU usage.- Memory consumption.- Disk utilization.- Network activity.- Application errors.- Active processing sessions.## NFR-DEP-008: Deployment SecurityProduction services shall expose only necessary network ports.Administrative access shall be restricted and secured.---# 11. Export and Offline Storage Requirements## NFR-EXP-001: Export PerformanceThe application shall generate exports within reasonable time limits based on dataset size.## NFR-EXP-002: Export IntegrityGenerated files shall preserve the accuracy of the underlying analytical results.## NFR-EXP-003: Export StructureComplete analysis packages shall follow a consistent directory structure and include a metadata manifest.## NFR-EXP-004: Offline PortabilityDownloaded packages shall be independently accessible without requiring an active SSIP session.## NFR-EXP-005: Export SecuritySensitive information shall be handled according to the user's authorization level.---# 12. Resource and Capacity ConstraintsThe initial deployment shall be designed around the selected VPS configuration.Resource usage shall be measured rather than assumed.The application shall enforce:- Maximum upload size.- Maximum records per analysis session.- Maximum concurrent processing jobs.- Maximum active temporary sessions.- Session expiration duration.- Temporary export storage limits.If processing capacity is exceeded, the application shall reject or defer additional work gracefully rather than crashing.These limits shall be configurable.---# 13. Initial Quality TargetsThe following values are provisional engineering targets and must be validated through testing on the actual deployment infrastructure.| Quality attribute | Initial target ||---|---|| Monthly availability | 99.5% || Initial page rendering | Under 3 seconds || Standard API response | Under 2 seconds || Dashboard filtering | Under 2 seconds || Processing 1,000 records | Under 5 seconds || Processing 5,000 records | Under 15 seconds || Processing 10,000 records | Under 30 seconds || Concurrent authenticated users | 50 || Simultaneous processing sessions | 10 || Communication security | HTTPS || Student assessment retention | Temporary only || Session cleanup | According to configured expiry policy |Performance targets shall be measured under documented test conditions and representative dataset sizes.---# 14. Non-Functional Acceptance CriteriaThe initial release shall satisfy the following conditions:1. The website loads reliably over HTTPS.2. Protected routes enforce authentication and authorization.3. Departmental access restrictions cannot be bypassed through API requests.4. Uploaded files are validated before processing.5. Processing sessions remain isolated.6. Dashboard interactions meet the defined performance targets under test conditions.7. Concurrent sessions remain within configured resource limits.8. Temporary assessment data is removed after session expiration.9. Sensitive student information is not unnecessarily retained in logs or browser storage.10. Reports-only exports exclude identifiable student information by default.11. Complete analysis packages preserve the required analysis data and metadata.12. Application failures produce understandable error responses.13. Server resource utilization is monitored.14. Production deployment follows the approved security configuration.---# 15. Requirement Review and Change ManagementNon-functional requirements shall be reviewed whenever changes affect:- Hosting infrastructure.- Session management.- Data processing architecture.- Authentication.- Security controls.- Dataset capacity.- Concurrent user capacity.- Export generation.- Data retention.Every approved change shall be documented in DECISIONS_LOG.md and reflected in the relevant architecture documentation.---**End of NON_FUNCTIONAL_REQUIREMENTS.md**
